FMI / AKAYADMIN - GROK AGENT INTEGRATION HANDBOOK
Version 1.0 | Prepared 4 November 2026 | Production API

This is a self-contained integration handoff: connection instructions, reporting rules, examples for all seven accepted record kinds, and the complete OpenAPI 3.1 specification. No other file is required to understand the integration. No API key or owner password is included.

1. PURPOSE AND CURRENT BOUNDARY

Send genuine organic business inquiries, competitor/AEO observations, content drafts, and authorized work updates into FMI's owner dashboard. Production dashboard: https://findmyinvite.com/akay

This is a scoped WRITE API. Grok cannot use it to read the private dashboard, list customers/orders/tickets, obtain sales figures, or retrieve current record revisions. The owner must supply any necessary identifiers, existing record payloads, revisions, or exported business data. Do not pretend to have inspected unavailable business data.

There is no arbitrary free-form insight endpoint. Submit dated research through observation records, with facts in evidence and interpretation/recommendations in notes. Organic charts and trends are computed from daily reports and matched lead records. Content recommendations may be submitted as article ideas/briefs/drafts. Do not send unsupported record kinds or invented fields.

2. OWNER CONNECTION CHECKLIST

A. Sign into /akay. Under Team & Agents, add Grok as an Agent.
B. Under Settings & Connections > External agent keys, choose a name, the Grok agent, and the required permission. For operations, select the assigned projects. Create the key and copy it once into Grok's secure secret settings.
C. Use separate keys per responsibility. Suggested secret names: FMI_ORGANIC_API_KEY, FMI_RESEARCH_API_KEY, FMI_CONTENT_API_KEY, FMI_TICKETS_API_KEY, FMI_RUNS_API_KEY. These are suggested names in Grok's runtime, not additional FMI settings.
D. Configure expected organic accounts in Settings using the exact platform/account strings Grok will report. Otherwise account coverage cannot be interpreted reliably.
E. Supply Grok with the real platform account identifiers and any required FMI resource, project, ticket, benchmark, customer, order or template IDs. Do not guess IDs.
F. Send dryRun:true first. Inspect every result. After validation, send real collected data with dryRun:false. Verify the first accepted report in Organic Leads and the first observation in Search & Content.

No key is created by this document. Store keys outside prompts and source code. Never use the AkayAdmin password as an API credential. Revoke a compromised key in Settings. No permission permits customer-message sending, financial administration, public article publication, advertising spend, or owner login.

3. ENDPOINT AND AUTHENTICATION

POST https://findmyinvite.com/api/owner?action=ingest
Authorization: Bearer <OWNER_ISSUED_AGENT_KEY>
Content-Type: application/json

Use server-to-server HTTPS. Owner cookies are not required. All records in a request share one kind:
{"kind":"daily","dryRun":true,"records":[...valid records...]}

Accepted kinds / required scope / destination:
- daily, lead / organic:write / Organic Leads and customer-footprint reporting
- observation / research:write / Search & Content competitor and AEO records
- article / content:draft / Search & Content editorial workflow
- ticket / tickets:write / Existing assigned tickets in Projects & Kanban
- run, time / runs:write / Team & Agents and Calendar & Time

Limits: 100 records per request, 500,000-byte request body, 300 requests per minute per key. Use small batches. Unknown data fields are rejected. JSON numbers must be numbers, not numeric strings. Timestamps in the examples use ISO 8601 UTC with Z. Monetary cost fields use integer paise: Rs.1.18 = 118. Do not invent costs; omitted cost defaults to zero and is not proof of zero actual spend.

dryRun validates without saving business records. It consumes request allowance and does not reserve identities or guarantee that a later write will pass concurrency checks. All examples below are hypothetical and deliberately use dryRun:true. Replace sample facts and placeholder IDs before any write.

4. DAILY ORGANIC REPORTING RULES

A lead/inquiry means someone asking about invitations, price, availability, personalisation or purchasing. Likes, emojis and casual comments are engagement, not business inquiries.

Send one replacement snapshot per platform/account/business date. Use date YYYY-MM-DD and timezone Asia/Kolkata. Keep platform/account capitalization and spelling stable. Row identity is platform + account + date; sourceReportId is provenance, not a second account total.

sourceRevision starts at 1 and increases only when the report changes. Send the full corrected totals, never an incremental delta. An exact retry with the same revision/payload is idempotent. Older revisions, or changed data at the same revision, are rejected with a conflict. Network retries must preserve the original payload and revision.

commentInquiries + dmInquiries counts inquiries, not necessarily unique people. uniqueInquirers is optional and requires reliable deduplication; it cannot exceed their sum. Do not infer unique people from display names. Account totals and optional per-post breakdowns are separate views; never add them together. Individual lead records enrich daily totals and are never added to them.

Use complete:false for incomplete collection and complete:true only when the stated business day is fully covered. Missing reports mean UNKNOWN, never zero. A complete zero report means no inquiries were found after actual collection. Today's data remains 'so far' until complete. Configure expected accounts so yesterday can be flagged overdue after 10:00 IST.

cutoff is the collection coverage cutoff; collectedAt is when collection completed. cutoff must not exceed collectedAt. collectedAt cannot be more than ten minutes ahead of server time. Future business dates are rejected. 23:59:59 IST is 18:29:59Z on the same calendar day. Do not label a partial day complete.

Optional reach and engagement require measured source data. posts supports at most 500 distinct postId entries; each can contain url, inquiry counts and optional reach. Do not add fields such as campaign, impressions or language to daily reports unless a future contract explicitly supports them.

Trends require complete coverage: compare seven complete calendar days against the preceding seven. Missing coverage is insufficient evidence, not decline. Default attention rules are three complete zero-inquiry days, or at least a 30% seven-day decline when the previous period had at least ten inquiries. Thresholds are owner-configurable. Visits, inquiries and purchases overlap and must never be added into a fabricated total customer count.

5. INDIVIDUAL LEADS

Lead data requires externalId, contactId, platform, account, channel (comment or dm), and firstInquiryAt. Use stable external inquiry identifiers and reliable stable contact identifiers. Keep records distinct unless identifiers or owner-approved merges justify joining them. Do not ingest full DM transcripts by default.

Statuses: New, Responded, Quoted, Won, Lost.
Intent: invitations, price, availability, personalisation, purchase, other inquiry.
Optional fields include postUrl, templateId, language, notes, firstResponseAt, customerId, orderId. Link only real known FMI records. A response timestamp must be actual and not precede the inquiry. Conversion and revenue only describe the reliably matched subset, not all reported inquiries. Lace & Pearls currently uses templateId ivory-lace.

6. RESEARCH, AEO AND CONTENT

Observations require name, kind (Competitor or AEO), subject, locale, observedAt and evidence. Provide a sourceUrl whenever possible and explain what it supports. Separate sourced facts from inference and recommended action in notes. Do not claim competitor traffic, revenue, backlinks or market share without an identified source; label estimates.

For AEO, use the exact owner-provided benchmarkId, current benchmarkRevision and question, with matching locale. Supply engine, surface, mentioned and citedUrl based on actual observations. Supported surfaces: Search, Assistant, API experiment, Website. Keep consumer assistant/search observations separate from API experiments. Mention and citation are different; citedUrl is the actual FMI citation, if any. Comparable fixed-benchmark observations support citation-rate reporting, not a universal AI rank.

Observation identity depends on agent + sourceUrl + observedAt. Different observations with the same URL/timestamp can conflict; retain distinct genuine evidence references and real observation timestamps. Do not fabricate timestamps to bypass conflicts. No externalId field exists for observations.

Articles accept Markdown body, name, slug, author, language and status, with optional excerpt, notes, query, cluster, metaDescription and relatedTemplates. Agent status is restricted to Idea, Brief, Draft or Review. Only the owner approves, schedules and publishes. Use original, sourced content; preserve existing article URLs. Stable slug identifies the article within the agent's namespace. Published slugs are immutable. Article drafts do not become public simply because ingestion succeeds.

7. ASSIGNED WORK REPORTING

Ticket updates require an existing assigned ticket ID, current FMI revision, and the full ticket data. The agent cannot create tickets here or reassign them. Both its resource assignment and allowed project must match. Stages: Backlog, Ready, In progress, Review, Blocked, Done. Priorities: Low, Medium, High, Urgent. Use notes/checklist for actual progress; do not claim unperformed work.

Runs require stable externalId, name, resourceId, assigned projectId, status and occurredAt. Run statuses: Running, Complete, Failed, Blocked. Time entries require stable externalId, name, resourceId, assigned projectId, date and minutes (1-1440). Optional cost is integer paise; optional costSourceId supports cost reconciliation. Runs may include resultUrl. Do not report the same incurred cost in multiple records without an appropriate common reconciliation reference.

8. RESPONSES, REVISIONS AND RETRIES

HTTP 200 can contain rejected records. Inspect results individually:
{"dryRun":false,"receivedAt":"2026-11-04T09:00:00Z","results":[{"index":0,"accepted":true,"id":"FMI_RECORD_ID","revision":1,"reportRevision":1,"duplicate":false}]}

A rejected result includes index, accepted:false, error and status. reportRevision applies to daily reports. FMI revision is the stored record concurrency revision; it is distinct from the daily sourceRevision. Dry runs may not return persisted IDs/revisions.

For a non-daily first write, normally omit id/revision. Persist the returned FMI id/revision and the full canonical payload. To update, send:
{"kind":"lead","dryRun":false,"records":[{"id":"RETURNED_ID","revision":1,"data":{...FULL_VALID_LEAD_DATA...}}]}

Updates are full records, not patches. Omitted optional/defaulted fields can clear previous data. Preserve the complete intended state. Exact retries deduplicate by stable identity and normalized payload. Do not substitute a different key/agent namespace to evade a conflict. A stale revision requires the owner to provide the current record and revision; this API has no agent read endpoint.

400: correct invalid fields. 401: check missing/invalid key. 403: check permission, revoked key, resource/project restrictions. 409: resolve revision/identity conflict; do not overwrite blindly. 413: split request. 429: honor Retry-After if supplied, otherwise wait at least 60 seconds. 5xx/network timeout: exponential backoff with jitter and the exact original payload/identifiers. Retry only failed or unconfirmed records. Stop repeated failures and report the issue to the owner without exposing secrets.

9. PRACTICAL OPERATING ROUTINE

- Use only sources/accounts the owner authorized Grok to access.
- Collect real inquiries; submit partial daily snapshots while collection is incomplete, with increasing revisions as totals change.
- Submit the previous day's complete snapshot before 10:00 IST where practical; send explicit complete zeros only after verified collection.
- Submit optional detail leads using reliable identifiers; update statuses only when known.
- Submit dated competitor/AEO evidence against the owner's agreed benchmark. Do not manufacture observations for missing providers.
- Summarize coverage, measured changes, uncertainty and concrete recommendations. Request owner data for private revenue comparisons that this API cannot read.
- Submit drafts for owner review; no autonomous publication or spending.
- Persist successful IDs/revisions in Grok's own integration state and monitor every API result.

FMI ingestion does not schedule Grok or grant social-platform access. Scheduling and authorized source collection must be configured separately in the external Grok runtime.
